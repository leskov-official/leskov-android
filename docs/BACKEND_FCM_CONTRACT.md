# LESKOV Native Push — что необходимо сделать на сервере

## Проверенный факт

В исходном экспортированном Android-проекте `app/google-services.json` был **поддельным** (`AIzaSyFake...`, project_number `100000000000`). В первоначальном PHP-архиве LESKOV есть Web Push (`sw.js`, VAPID), но это не означает наличия готового FCM backend. Предложенные Gemini URL `profile.php?ajax=register_fcm_token` / `unregister_fcm_token` не были подтверждены в исходном PHP-коде. Предыдущие запросы без cookies и CSRF передавали `user_id` из клиента, что было бы небезопасно.

## Правильный backend-контракт (предложение, НЕ существующий API)

Создать на сервере HTTPS endpoint для регистрации токена, доступный только пользователю с действующей серверной сессией LESKOV. URL выбрать вместе с разработчиком PHP. Запрос — `POST` с CSRF-защитой и `credentials: include` при вызове из first-party WebView либо с другой проверенной схемой клиентской аутентификации. В теле: токен FCM, версия клиента, язык, идентификатор устройства (псевдоним без лишних персональных данных). **Не принимать `user_id` как доказательство личности:** user ID сервер должен получить из действующей авторизованной сессии.

Хранить только хешированный/зашифрованный либо защищённый FCM token с owner user ID, временем обновления и состоянием. Сделать endpoint для отписки при явном выходе, смене аккаунта, отзыве разрешений; удалять просроченные токены при `UNREGISTERED` от FCM. Реализовать rate limit, CSRF, проверку происхождения и аудит без публикации токенов в логах.

На события сервера (личное сообщение, заявка, реакция, комментарий, публикация, входящий звонок) отправлять сообщение через **Firebase Cloud Messaging HTTP v1** из backend с аутентификацией service account **ТОЛЬКО на сервере**. Service account JSON и приватный ключ нельзя хранить в APK, ZIP или клиентском JavaScript. Проверять, кто имеет право получать каждое событие и какие детали можно выводить на заблокированном экране.

Для звонка нужны verified `call_id`, sender id, срок жизни, состояние звонка и token nonce. Кнопки «Принять»/«Отклонить» добавлять только после реализации безопасного серверного действия — переход к странице вызова не равнозначен его принятию. TTL входящего вызова короткий, отменённый звонок должен удалять или инвалидировать уведомление.

## Проверка

1. Реальный `google-services.json` успешно создаёт FirebaseApp, `FirebaseMessaging.getInstance().token` возвращает действительный токен.
2. POST регистрации получает 200, сервер сохраняет токен за текущим **авторизованным** пользователем.
3. С другого аккаунта отправить сообщение; уведомление получено при открытой Activity и при приложении в фоне.
4. Проверить закрытую Activity, заблокированный экран, отключённые разрешения и перезапуск устройства.
5. После выхода из аккаунта push старого пользователя не приходит.
6. Настройки уведомлений по категориям работают; звуковые и текстовые детали соответствуют privacy.

До этих шагов **нет подтверждённой доставки нативных push**. В Android-проекте endpoint сознательно оставлен как неактивная точка интеграции, а не вымышленный «успешный» запрос.
